# Event Registration & Seat Hold Architecture

This document explains the technical logic behind the event registration system and how we handle concurrency, seat holds, and payments without double-booking.

## 1. The Core Problem
When dealing with limited-seat events and manual payments (like UPI), we must ensure that a user does not complete a payment for a seat that just got taken by someone else a few seconds prior. We also need to avoid "Optimistic Holding" (where users spend 5 minutes filling out a form only to be rejected at the very end when they click Submit).

## 2. The "Draft" Approach (15-Minute Seat Holds)
To solve this, we use a 15-minute temporary seat hold system:
1. **Selection:** The exact moment a user selects an event from the dropdown, the frontend fires a request to the Supabase backend (`hold_seat` RPC).
2. **Locking:** The backend checks seat availability. If a seat is available, it decreases the available count temporarily and grants the user a unique `hold_token` with an `expires_at` timestamp exactly 15 minutes in the future.
3. **Safety Window:** The user now has a guaranteed 15-minute window to fill out their details, scan the QR code, make the UPI payment, and submit their UTR number. As long as they submit within this window, the seat is 100% theirs. 

## 3. Frontend Persistence & Recovery (sessionStorage)
Handling page reloads is a classic web challenge. If a user reloads the page, we don't want them to accidentally grab a *second* 15-minute hold while their first one gets stuck in the database.

* **Caching:** When the backend grants a hold, the frontend saves the `hold_token` and `expires_at` timestamp into the browser's `sessionStorage`, keyed by the specific event ID (e.g., `hold_81aae...`).
* **Recovery:** When the Registration page mounts, it first checks `sessionStorage`. If a valid, unexpired hold exists for the selected event, the frontend instantly restores the timer and skips the backend call entirely. 
* **Precision:** Because we store the absolute `expires_at` timestamp generated by the backend, the timer resumes exactly where it left off (e.g., 12m 45s) rather than restarting at 15 minutes.

## 4. Successful Registration & Token Cleanup
When the user submits the form with their UTR:
1. The frontend sends the user data and the `hold_token` to the backend.
2. The backend validates the token, permanently registers the user, and consumes the seat.
3. **Cleanup:** Once the frontend receives a success response, it instantly deletes the `hold_token` from `sessionStorage`. 
4. **Back-to-Back Registrations:** Because the token is wiped on success, the user can immediately go back to the registration page and register a friend for the *exact same event*, and the system will correctly fetch a brand new seat hold for them.

## 5. React Strict Mode Protection
In React 18 development, `useEffect` fires twice. To prevent the frontend from accidentally pinging the Supabase backend twice and generating two simultaneous holds for one user, we implemented a `useRef` lock (`holdInProgress`) that guarantees the API is strictly called once per event selection.

## 6. Abandoned Seats
If a user closes the tab without completing the registration, the `sessionStorage` is destroyed (as it is tied to the tab session). The seat remains locked on the backend for the remainder of the 15 minutes. Once the 15 minutes pass, the backend automatically releases the seat back into the wild for another user to claim. This guarantees no seats are ever permanently lost due to browser crashes or abandoned forms.
